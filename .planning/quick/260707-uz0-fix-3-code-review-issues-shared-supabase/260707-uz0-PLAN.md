<objective>
Fix three code-review issues in the Atmaram hospital site:
1. Replace three per-instance in-memory rate limiters with a single shared, Supabase-table-backed, race-safe counter so limits survive across serverless instances.
2. Reject chat requests that arrive with no Origin header (close the null-origin bypass).
3. Consolidate the staff self-lockout guard so both `updateStaffAction` and `toggleActiveAction` enforce it.

Purpose: Rate limits currently reset on every cold start and are per-instance, making them ineffective on serverless; the origin-null default lets scripted clients bypass CORS; and the self-lockout guard exists in only one of two code paths that can set `is_active: false`.

Output: New migration + shared rate-limit module, three migrated call sites, one auth-logic fix, one shared guard helper.
</objective>

Create `supabase/migrations/20260707_rate_limit_counters.sql` (idempotent, matching existing migration header-comment style):
- `create table if not exists rate_limit_counters (key text primary key, count int not null default 0, window_start timestamptz not null default now());`
- A `create or replace function check_rate_limit(p_key text, p_max int, p_window_ms int) returns boolean` that performs a SINGLE atomic upsert to avoid TOCTOU races. Logic (fixed window): `insert into rate_limit_counters(key, count, window_start) values (p_key, 1, now()) on conflict (key) do update set count = case when rate_limit_counters.window_start < now() - make_interval(secs => p_window_ms / 1000.0) then 1 else rate_limit_counters.count + 1 end, window_start = case when rate_limit_counters.window_start < now() - make_interval(secs => p_window_ms / 1000.0) then now() else rate_limit_counters.window_start end returning count into v_count;` then `return v_count <= p_max;`. Declare `v_count int;` and mark the function `language plpgsql`. Returning true = allowed, false = over limit — matching each call site's existing "true means proceed" convention.
- Add a comment noting the SQL must be applied via the Supabase SQL editor (see Task 2).

`export async function checkRateLimit(key: string, opts: { max: number; windowMs: number }): Promise<boolean>` — calls `createAdminClient().rpc('check_rate_limit', { p_key: key, p_max: opts.max, p_window_ms: opts.windowMs })`. On RPC error, log via console.warn and FAIL OPEN (return true) so a transient DB hiccup never hard-blocks legitimate users — but the origin/captcha/auth checks remain the real gates.   <name>Task 5: Harden chat route against token-exhaustion / rapid-fire abuse</name>
  <files>app/api/chat/route.ts</files>
  <action>
Four additive fixes to `app/api/chat/route.ts`, on top of Task 3's rate-limit swap and Task 4's origin fix. Do not change unrelated behavior (validation error messages, status codes for existing checks stay as-is).

1. **First-hop IP extraction (spoofable multi-hop bug):** the current `const ip = request.headers.get('x-forwarded-for') ?? request.headers.get('x-real-ip') ?? '127.0.0.1'` uses the RAW header value (could be a comma-separated chain), unlike `auth.ts` and `submitAppointmentAction.ts` which already do `.split(',')[0]?.trim()`. Change to match that existing pattern: `request.headers.get('x-forwarded-for')?.split(',')[0]?.trim() ?? request.headers.get('x-real-ip') ?? '127.0.0.1'`. This does not fully close IP spoofing (that requires trusted-proxy infrastructure config, out of scope here) but brings this file in line with the other two call sites' existing convention and stops a chain string from being used as-is.

2. **Cap Gemini output tokens:** in the `ai.models.generateContentStream` call (~line 128-132), add `maxOutputTokens: 500` inside the `config` object alongside the existing `systemInstruction`: `config: { systemInstruction: HOSPITAL_KNOWLEDGE, maxOutputTokens: 500 }`. A hospital-FAQ chatbot response has no legitimate need to exceed this.

3. **Bound total conversation character budget, not just per-message/per-count:** after the existing per-message length loop (~line 95-117) and before `const safeMessages = messages.slice(-20)`, add a total-size check across `safeMessages` (compute AFTER the slice, so it reflects what's actually sent to Gemini): sum `.content.length` across `safeMessages` and if the total exceeds `6000` characters, return the same shape of 400 error already used elsewhere in this file (`Response.json({ error: 'Conversation too long. Please start a new chat.' }, { status: 400 })`) BEFORE calling `generateContentStream`. Add a named constant `MAX_TOTAL_CONVERSATION_CHARS = 6000` near the existing `MAX_MESSAGE_LENGTH` constant.

4. **Abort generation when the client disconnects:** in the `ReadableStream`'s `start(controller)` (~line 134-150), check `request.signal.aborted` inside the `for await (const chunk of stream)` loop and `break` out early if true (before `controller.enqueue`), so the loop stops pulling further chunks once the client is gone. Since the underlying Gemini SDK stream object doesn't expose an explicit `.cancel()`/abort method in this codebase, breaking the consuming loop is the correct scope here — do not attempt to add SDK-level cancellation support beyond what `@google/genai`'s public API in this file already surfaces. Add a one-line comment explaining why (stop enqueueing to a dead controller / stop paying for tokens nobody will read).
